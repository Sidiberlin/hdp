# Investigation — `git status` Noise from `setup.sh`

## TL;DR

The ~1195 uncommitted paths under `app/extensions/`, `app/vendor/`,
`app/composer.lock`, and `app/skins/` are entirely generated by `setup.sh`
(composer, npm/language-pack refresh, upstream unicode-normalization of
filenames). None of it is human authorship. Leave it uncommitted for
this fixup PR — the correct long-term fix is a targeted `.gitignore`
expansion plus a one-time re-baseline commit, done in a separate cleanup
PR.

## What's actually in the noise

`git status --porcelain` breakdown (1195 total):

| Status | Count | What                                                     |
| ------ | ----- | -------------------------------------------------------- |
| `M`    | 247   | Mostly i18n JSON files + `composer.lock`                 |
| `D`    | 22    | Files upstream deleted between v4 and v5.1.3             |
| `??`   | 926   | Files upstream added between v4 and v5.1.3 + skin refreshes |

## Where the noise comes from

1. **`composer install`** in `setup.sh` step [1/4] rewrites
   `app/composer.lock` (45k-line churn: 22764+/22867-). This is a natural
   consequence of `composer install --prefer-dist` re-resolving against
   the current mirror — not a bug in the script.

2. **`.smw.json` writes**, `chown -R www-data`, and MediaWiki
   `update.php` will touch cache/l10n files under
   `extensions/BlueSpiceFoundation/data/` and `SemanticMediaWiki/data/` —
   but those are inside `app/cache/` which is already `.gitignore`d.

3. **i18n / language-pack refreshes** (`CodeMirror/i18n/*.json`, etc.)
   are re-written by BlueSpice's build tooling during install; the diffs
   are single-character author-list edits (e.g. adding `"Mohammed Qays"`
   to the translator credits array).

4. **`mw-config/overrides/*` deletions** (22 files) are legitimate
   upstream removals between the v4.5.3-beta release commit
   (`ebfb9b5b7`) and the v5.1.3 release commit (`97c8bc126`). The v5
   release commit already deleted these files upstream, but they remain
   on disk in the current checkout because git preserved them from the
   v4 baseline. `git log` on `app/mw-config/overrides/README` confirms
   the file exists ONLY in the v4 release commit.

5. **`Startpage_*` filename mangling**: three files show as both `D`
   (git-tracked with `#U00fc`-escaped names) and `??` (untracked with
   proper unicode names). Git is treating the escaped-name and
   unicode-name variants as different paths; on-disk state has the
   unicode form after setup.sh runs.

6. **`app/skins/*` new untracked files** appear because the previous
   agent's `.gitignore` fix whitelisted the shipped skin dirs
   (`BlueSpiceDiscovery/`, `hdp/`, etc.). Files that arrived via the
   v5.1.3 release commit under those dirs (i18n additions, package-lock
   updates) had been hidden by the old `/*` blanket ignore; now the
   whitelist exposes them.

## Are they tracked upstream?

Yes — `git log --oneline -- app/composer.lock` shows both v4.5.3-beta
(`ebfb9b5b7`) and v5.1.3 (`97c8bc126`) release commits touch this file.
Same for `app/extensions/CodeMirror/i18n/ar.json`. These paths ARE part
of the shipped release; the diff you see is `setup.sh`'s re-resolution
producing minor differences from the exact release-committed content.

## Recommendation

**For this PR (fixup / publication-readiness):** leave the noise
uncommitted. It's not your work, it's not a regression, and re-baselining
1195 files as part of a doc/typo-fix PR would obscure the actual
changes. The task brief already says explicitly not to commit it.

**For a follow-up cleanup PR (separate work):**

1. Add `app/composer.lock` to `.gitignore`? — No. Composer needs
   deterministic lock files; the fork should re-baseline it whenever
   `composer.json` intentionally changes. But the fork could commit ONE
   snapshot post-setup as the baseline and treat subsequent drift as a
   real change.

2. **One-time re-baseline commit** — after a clean `setup.sh` run on the
   maintainer's machine, `git add app/composer.lock` +
   `git add app/extensions/*/i18n/*.json` + the `Startpage_*` deletions
   + the new `app/skins/*/i18n/*.json` files, commit as
   `"chore: re-baseline generated files after v5.1.3 upgrade"`. Then
   future `setup.sh` runs will produce zero diff.

3. **Optional `.gitignore` additions** if step 2 feels wrong: add
   `app/extensions/*/i18n/`, `app/extensions/*/package-lock.json`, and
   `app/extensions/*/tests/` — but this hides legitimate upstream
   translation drift from PR review.

The maintainer should pick between approaches (2) and (3). Approach (2)
is cleaner but requires committing ~950 files in a single "re-baseline"
commit that reviewers will skip. Approach (3) is smaller but permanently
opts the fork out of upstream translation updates unless someone
manually pulls them.

## Files NOT to touch in this fixup PR

- `app/composer.lock` (unchanged human intent)
- `app/vendor/**` (already ignored)
- `app/extensions/**/i18n/*.json` (upstream refresh)
- `app/extensions/**/package-lock.json` (upstream refresh)
- `app/extensions/**/tests/**` (upstream additions)
- `app/mw-config/overrides/**` (upstream deletion)
- All `.eslintrc.json`, `.stylelintrc.json`, `.phpcs.xml`, `Gruntfile.js`
  additions under `app/extensions/` and `app/skins/` (upstream tooling
  files added in v5.1.3)
